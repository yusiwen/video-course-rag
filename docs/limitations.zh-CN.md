# 已知限制（alpha）

用自己的素材前先读这里。以下每条都是在搭建过程中实测到的，不是推测。

## 平台

- **macOS 用 Vision，Linux 用 RapidOCR，两者不能互换**：`native/ocr/ocr.swift` 链接
  Apple Vision、用 `swiftc` 现编；Linux 侧由 `ocr/rapid.py` 跑 RapidOCR，模型随 wheel
  附带。两边输出同一形状——`{text, conf, x, y, w, h}`、归一化、原点左下——因为下游依赖
  它：页眉是 `y > 0.86`，角落 logo 是 `x > 0.78 and y > 0.82`。RapidOCR 报的是左上
  原点的像素坐标，所以 `rapid.py` 出口把 `y` 翻过来。
- **RapidOCR 更慢、更脏，而且脏在启发式会在意的地方**：同样两帧，它要 1.0–1.8 秒
  （Vision 0.1–0.2 秒），并且多检出 4–11 行，因为它把工具栏图标读成了文字（`PAQ`、
  `最小化`）。92 分钟课程的画面分段因此要 22 分钟，而不是 3 分钟。
- **换引擎就会换出另一个标题带**：标定按「每帧最高的一行」拼出每个模式的标题带。
  PP-OCR 在 PowerPoint 窗口里给出的最高框是功能区标签，于是带子落在 y 0.885–0.965，
  259 个单元里 233 个被命名成工具栏按钮（「剪切」「文字方向」）或产品名。这类带子现在
  被判为窗口 chrome 并拒绝，单元退回中性标题——叫「工具栏」比叫「幻灯片（4 分钟）」更糟。
- 转写（`funasr`）跨平台，也是 `ingest` 里唯一需要装第三方依赖的一步（含 torch 约
  1.2 GB）。有 CUDA 时 RTF 0.0036（92 分钟音频 19.7 秒），CPU 是 0.32，且两者文字相同。
- **画面这一侧，GPU 不是那个杠杆，识别批大小才是。** RapidOCR 的 torch 引擎用同一套
  PP-OCR 模型跑 CUDA，不需要新装包（torch 本来就在），确实能砍半单帧成本——但第一轮 A/B
  只有 1.6–2 倍，值不上多一条推理路径。拆开才看清原因：CUDA 上一帧 1072 ms 里检测只占
  130 ms，识别约占 **87%**，而识别按批大小 6 在跑——121 行的画面要 21 次小前向。批设成
  32 后同一帧是 343 ms（5 次中位），onnxruntime/CPU 是 2550 ms；而且**CPU 引擎单靠这一项
  就从 2550 降到 1495 ms**。批 16 在某次测量里反而比 6 慢，所以这条曲线要实测、别假设单调。
- **torch 引擎要首次下载，onnxruntime 不用。** torch 权重里既没有字符字典，也没有
  onnxruntime 内嵌的那些元数据，所以 RapidOCR 会从 ModelScope 拉权重（det 10.2 MB、
  rec 21.3 MB、cls 0.6 MB）和 `ppocrv6_dict.txt` 到 `VIDEO_RAG_OCR_MODELS`（一次性约
  32 MB）。够不到 ModelScope 的机器会在构造时就失败，而不是在第一帧。
- **RapidOCR 下体检用的"外壳词表"会把真实主题吸进去，而规则必须学会不因此判死标题。**
  外壳（chrome）是靠统计"在多单元里重复出现的 OCR 行"学出来的；Vision 下这些行是窗口家具，
  而 RapidOCR 下单元的行里混着功能区标签，于是**同时**也是幻灯片主题的词也能越过阈值——某门课上
  `模型定义` 就是这样，它既是功能区附近的常驻词，也是真实主题。旧的近似规则（长度差 ≤6 且相似度
  0.75）于是把**仅仅包含**它的交付标题（`业务模型定义`、`模型内容定义`）判成 `chrome_variant`，
  而这是 EXPO，会拦住交付。现在窗口按长度成比例（0.85 相似度、1 个字符的余量）——那才是 OCR
  抖动真正会动的那一点（`SACME 平台名称` 对 `ACME 平台名称` 是 0.93）；标题里**嵌着**一个标签属于
  拼接，不是变体。改完五门课 EXPO 全 0、交付标题一字未变；退化层 RISK 在 RapidOCR 上仍然很高
  （128/19/75/0/0 对 Vision 的 0–3），因为那一层本来就是单元标题，而在这个平台上它们是功能区标签。
- **`jump` 只对"有名字的单元"有定义。** 这一步要找的是"哪一秒的 OCR 能重新读出这个单元的
  标题"，但循环对每个单元都扫：参考课上 246 个单元里 231 个没有标题，每帧相似度恒为 0，
  扫满九帧后返回的还是它本来就有的起点。那是 1795 次 ffmpeg 抓帧加 1795 次 OCR，约 22
  分钟，用来复现一个提前返回就能直接给出的答案。跳过无标题单元后该阶段变成 21 帧、15.6 秒，
  且 246 个单元的 `jump` / `jump_lag` / `jump_title_match` **逐值零差异**。
- **优化之前先知道一个阶段由什么构成。** `chapter` 是 settle + table + llm_chapters + fuse，
  在有 CUDA 的机器上实测 340 s / 0.06 s / 0.04 s / 0.40 s——另外三步是舍入误差，所以
  "chapter 慢"这句话只等价于"settle 慢"。settle 的成本是 帧数 ×（抓帧 + OCR），GPU 路径下
  一帧约 0.74 秒，其中 OCR 约 0.34 秒、其余是一次新的 ffmpeg seek。
- **换引擎动的是单元合并，不是边界。** 同一门课 onnxruntime/CPU vs torch/CUDA：243/243
  个单元落在 ±2 秒内、243/243 模式不变，但有 71 个单元标题不同——两边都是工具栏或产品名
  这类垃圾（那个模式本来就没有标题带）——于是"相邻同标题则合并"这条规则给出 259 vs 249
  个单元。真正要紧的是交付表：35/35 章、35/35 标题一致、18/35 起点完全相同（最大偏移
  11.6 秒，其余不到 1 秒，来自吸附到不同的单元起点）。

## 切章表换机器复用

- **`start_sentence` 只在产出它的那次 run 里有效**：LLM 表存的是句子序号，而换一台机器
  （或另一个 torch 构建、另一个 FunASR 版本）断句会略有不同——同一段音频 macOS 切出
  867 句、Linux 切出 873 句，而转写文字相似度是 0.9998。第一个被移动的断句之后，每个
  章起点都指向错误的句子，误差还会累积：35 章里有 12 章漂了，到课程末尾偏到 47 秒，
  而所有标题都是对的。看起来像剪辑粗糙，不像 bug。
- 现在表里还存 `start_text`：章开始的那句话（句子太短如「嗯」时向后补齐到至少 8 个字）。
  融合层拿它去转写里做匹配，于是边界按「说了什么」来定位；旧表靠序号回退仍然能用。
- **修完之后仍然存在的差异**：画面吸附会把边界挪到附近的单元起点，而单元切分本身依赖
  引擎（macOS 246 个、Linux 259 个），所以还有 4 章与 macOS 位置相差 14 秒以内。chunk
  文本相似度约 0.68，是因为断句一变，同一段话被分进不同窗口——字是同一批字。

## 语言

- 断句、标题判定、界面文案都按中文讲座设计。标题过滤会丢弃不含 CJK 的行（除非在缩写表里），
  所以英文课现在只会产出中性章名而不是标题。这是支持非中文素材时第一个要改的地方。

## 检索

- 页面是**词面匹配**：讲师原话 BM25 + 章节标题 BM25，倒数排名融合。浏览器里没有查询编码器，
  所以同义改写可能打不中。实测：加章节通道后改写题的 rank-1 命中从 1/14 提到 6/14；
  稠密通道还能再提高，但在 `file://` 下跑不起来（bge-m3 是 566M 参数）。
- `vrag ask` 用同一套检索，再让 LLM 依据检索到的片段作答，需要使用者自填 API key。
  key 存在 `localStorage`，同机所有 `file://` 页面都能读到——设置对话框和包内 README 都写明了。
- 不要把 key 打进发行包：`vrag pack` 会扫描出包结果，命中 key 形态的串就拒绝完成。

## 出包

- 交付物就是一个 HTML 文件，这是刻意的。实测 120 小时约 28 MB，首屏 235 ms；
  检索成本不随课程数增长（索引按课程惰性重建）。
- 章名上限就是画面：素材里没有稳定标题行时（应用窗口、桌面操作），工具会故意给中性标签
  （如 `幻灯片（37 分钟）`）——编一个主题比承认没有更糟——并由 `vrag audit` 报出占比。

## 两种"看起来成功"的失败

这两条都是把本工具的输出与移植前的流水线逐项比对才发现的，共同点是：产物看起来正常，但内容是错的。

- **重名的导入被局部函数遮蔽。** 在一个已经定义 `ocr(png)` 的文件里写 `from ..ocr import backend as ocr`，模块绑到同一个名字上、被局部函数盖掉，于是每次 `ocr.read(...)` 抛 `AttributeError`，外面的 `try/except` 把它变成 `[]`——分段全程拿不到屏幕文字。不会崩，只是单元数悄悄变了、全部被判成 `desktop`。不要把 import 别名起成模块里已用的名字。
- **缓存无条件信任自己写下的内容。** 标定缓存保存了它见过的每一帧，包括 OCR 坏掉那段时间读到的空帧。空条目永远不会过期，于是被污染的词汇表比 bug 活得更久，持续改变"能找到哪个标题带"。只缓存成功的结果，空结果一律当作未命中。

## 泄漏闸门这次真派上了用场

这个仓库第一次扫描时被判定为"干净"，但它当时还带着真实材料：页面空状态文案里一句来自真实问答的说法、某函数注释里引用的转写原句、标题判据注释里的讲师姓名、一段 docstring 里的 ASR 误听、两个测试夹具里的真实章标题，还有一条来自讲师 Windows 桌面路径的注释。这些都不在 `runs/` 里，全部是作为"举例"被粘进代码的——真实材料正是这样漏出去的。

现在有两道约束让这件事不容易重演：黑名单里存着这些字符串，它们无法再悄悄回来；闸门也不再跳过 `pack/assets/`，其中一条就藏在那个目录里——目录级跳过是个从退出码看不出来的洞。
